# CLAUDE.md — backend

Django REST API for the flight-agency back office. See [`../CLAUDE.md`](../CLAUDE.md) for the
product overview and the frontend contract.

## Stack

- **Django 4.2.7**, **DRF 3.16.0**, **django-rest-knox 5.0.2** (token auth).
- **PostgreSQL only** (no SQLite). `psycopg` v3 + `psycopg2-binary` both pinned.
- `django-grappelli` (admin skin), `django-cors-headers`, `django-sortedm2m`
  (`Reservation.flights` ordered M2M), `dj-database-url`, `whitenoise`, `gunicorn`.
- Deploy: **Railway** (`Procfile`). `IS_PRODUCTION = "RAILWAY_ENVIRONMENT" in os.environ`;
  `DEBUG = not IS_PRODUCTION`.
- Single flat settings module `core/settings.py` (no `base/dev/prod` split).
- Lint: **flake8** only (`.flake8`, `max-line-length = 120`, ignores `E203,E701`). `black` is
  installed but **not configured and not run** — match existing style, don't reformat.
- `requests`, `sendgrid`, `PyJWT` are in `requirements.txt` but **unused** — there are **no external
  integrations** (no email, Celery, Redis, S3, payments, webhooks, flight/GDS API). Flight data is
  local DB rows generated by `populate_local`.

## Commands

```
python manage.py migrate
python manage.py runserver
python manage.py test --parallel          # the full suite; CI runs exactly this
python manage.py test agency.tests.test_reservations   # a single module
python manage.py populate_local           # DEBUG + no DATABASE_URL only; wipes & reseeds everything
flake8 .
```

CI (`.github/workflows/ci.yaml`, push/PR to `main`): Postgres service → `pip install -r
requirements.txt` → `flake8 .` → `migrate` → `test --parallel`. Python 3.11.

## App layout

| Package | Role | Key files |
|---|---|---|
| `core/` | Project config (**not** in `INSTALLED_APPS`) | `settings.py`, `urls.py` (root), `models.py` → `BaseModel.to_map()`, `admin.py` → `BaseAdmin` (role-gated), `utils.py` → `get_object_or_none()`, `only_digits()`, `check_max_length()`, `tests.py` → `BaseTestCase` |
| `users/` | Auth, users, roles, audit log | `models.py` (`User`, `InternalLog`), `views.py`, `serializers.py` (the only DRF serializer), `permissions.py` (`HasRole`), `backends.py` (`AuthBackend`), `managers.py`, `failures.py`, `urls.py` (named routes), `management/commands/populate_local.py` |
| `flights/` | Airlines, airports, flights | `models.py`, `views.py` (single module), `failures.py`, `urls.py`, `tests.py` (single module) |
| `agency/` | Core domain: customers, suppliers, sales, reservations, dashboard | `models.py`, `views/` **package** (`customers.py`, `suppliers.py`, `reservations.py`, `dashboard.py`), `failures.py`, `urls.py`, `tests/` **package** |
| `utils/` | Pure helpers (**not** an app) | `validators.py`, `formatters.py`, `test_utils.py` → `get_auth_header(role)` |

Root URLs (`core/urls.py`): `grappelli/`, `admin/`, `auth/` → `users`, `flights/` → `flights`,
`agency/` → `agency`.

**When an app grows past one resource, split `views/` and `tests/` into packages** (as `agency`
does — one module per resource). Small single-resource apps keep single modules.

## View pattern (the core convention)

Every endpoint is a **`rest_framework.views.APIView` subclass** with `get` / `post` / `put` /
`delete` methods. **No `GenericAPIView`, no `ViewSet`, no routers, no DRF serializers for I/O.**
(`users.LoginView` / `LogoutView` subclass knox's views — the only exception.)

Per resource, define a `*Mixin` that the `APIView`(s) inherit:

```python
class CustomerMixin:
    def serializer(self, obj):
        return {"id": obj.id, "name": obj.name, "email": obj.email, "phone": obj.phone}

    def validate_data(self, data, customer_id=None):
        # 1. required-field check -> (None, Response({..., "reason": <FailureReason>.value}))
        # 2. format validation via utils.validators (validate_email, validate_string, ...)
        # 3. uniqueness: Model.objects.filter(...).exclude(id=customer_id).exists()
        # 4. FK existence: core.utils.get_object_or_none(Model, id=...)
        return {"name": ..., "email": ..., "phone": ...}, None   # (validated_dict, error_response)


class CustomersView(CustomerMixin, APIView):
    permission_classes = (permissions.IsAuthenticated,)

    def get(self, request):
        data = [self.serializer(c) for c in Customer.objects.all()]
        return Response({"success": True, "items": data})

    def post(self, request):
        data, error = self.validate_data(request.data)
        if error:
            return error
        customer = Customer.objects.create(**data)
        return Response({"success": True, "message": "...", "customer": self.serializer(customer)})
```

- `validate_data` **always** returns a 2-tuple: `(validated_dict, None)` or `(None, Response(error))`.
- Multi-model writes wrap `transaction.atomic()` — see
  `agency/views/reservations.py::ReservationsView.post` (`Sale` + `Reservation` + `flights.set()`).
- `DELETE` is a **soft delete** (`obj.is_active = False; obj.save()`) for `Customer` / `Supplier`.
- Read endpoints hand-optimize queries: `select_related` / `prefetch_related` /
  `Prefetch(..., to_attr="prefetched_x")` (see `reservations.py`, `flights/views.py::NextFlightsView`).
- Aggregation/reporting logic goes in the view too — see `agency/views/dashboard.py`
  (`Sum` / `Count` / `F`, `get_base_queryset()` returns `(queryset, mode)` where `mode` is
  `"admin"` or `"seller"`).
- **New view = new `flights/views.py::FlightView` should NOT be the template** — it is the one
  resource that skips the Mixin and inlines ~150 lines. Use the Mixin pattern.

## URL pattern

Explicit `path()` in `<app>/urls.py`, one class per pattern, `.as_view()`, PK kwarg is **`<int:id>`**
(not `pk`). `users/urls.py` names its routes; `flights` / `agency` do not — follow the app you're in.

```python
urlpatterns = [
    path("customers/", CustomersView.as_view()),
    path("customers/<int:id>/", CustomerView.as_view()),
    path("suppliers/create/", CreateSupplierView.as_view()),   # create sometimes gets its own path
]
```

## Response envelope

- Success: `Response({"success": True, "message"?: str, "<resource_key>": <data>})`.
- Business error: `Response({"success": False, "message": str, "reason": <FailureReason>.value})`
  — returned at **HTTP 200** (current norm; see debt section).
- `reason` codes live in `<app>/failures.py` as `Enum` classes (`CreateCustomerFailureReason`,
  `CreateReservationFailureReason`, …). Add a member there before using a new code; tests assert on
  `<Enum>.MEMBER.value`.
- List key is per-endpoint (`items`, `suppliers`, `airlines`, `users`, …); create returns the
  singular (`customer`, `supplier`, `flight`). Prefer `items` for new list endpoints.

## Serialization

No DRF serializers for request/response bodies. Three tools, in order of preference:

1. **Hand-built `dict` in a `serializer()` / `serialize_<thing>()` method** on the view/Mixin — the
   standard. Nest by calling other `serialize_*` helpers (see `reservations.py`).
2. `core/models.py::BaseModel.to_map()` — generic reflection-based model→dict (handles dates,
   `Decimal`, FK, M2M). Available on every model; use for quick/admin-ish dumps, not for shaped API
   payloads.
3. `rest_framework.ModelSerializer` — **only** `users/serializers.py::UserSerializer`, wired via
   `REST_FRAMEWORK["USER_SERIALIZER"]` for knox login responses. Don't add more unless you're
   deliberately introducing the pattern.

## Validation

- Primitive validation: `utils/validators.py` (`validate_string`, `validate_email`, `validate_int`,
  `validate_list`, `validate_url`) — raise `django.core.exceptions.ValidationError`.
- Business validation: the `validate_data()` tuple pattern above. No `serializer.validate_*`,
  `.create()` / `.update()` overrides anywhere.
- `Flight.clean()` exists but is **not** run by the views (they `.objects.create()` directly and
  re-check rules by hand) — if you touch flight creation, prefer calling `full_clean()`.

## Auth & permissions

- **knox `TokenAuthentication`** — `REST_FRAMEWORK["DEFAULT_AUTHENTICATION_CLASSES"] =
  ("knox.auth.TokenAuthentication",)`. Header `Authorization: Token <key>`. No `REST_KNOX` dict →
  knox defaults (10h TTL). `LoginView` bumps TTL to 365 days when `keep_connected` is truthy.
- **Custom user** `users.User(BaseModel, AbstractUser)`: `username = None`,
  `USERNAME_FIELD = "email"`, `role` is a `TextChoices` (`admin` / `manager` / `seller`, default
  `seller`). `AUTH_USER_MODEL = "users.User"`. `AuthBackend` (sole `AUTHENTICATION_BACKENDS`) looks
  users up by email.
- **Permissions are per-view and explicit.** There is **no `DEFAULT_PERMISSION_CLASSES`**, so a view
  without `permission_classes` is public — always set it (usually
  `(permissions.IsAuthenticated,)`).
- **RBAC** = `users/permissions.py::HasRole` + a class attribute:

  ```python
  class CreateSupplierView(SupplierMixin, APIView):
      permission_classes = (HasRole,)
      ALLOWED_ROLES = [User.Role.ADMIN, User.Role.MANAGER]
  ```

  `HasRole` reads `view.ALLOWED_ROLES` — omitting it raises `AttributeError`.
- **Row-level scoping is done inside the view**, not in a permission class: sellers only see their
  own data (`dashboard.py`, `reservations.py` → `.filter(sale__seller=request.user)`);
  `GetUsersView` excludes admins. No `has_object_permission` anywhere.
- Audit: write a `users.InternalLog` row (`action`, `entity`, `entity_id`, `message`, `user`) after
  privileged mutations — see `CreateOrUpdateUserView`.
- Admin: subclass `core/admin.py::BaseAdmin` (gates every `has_*_permission` on `role == ADMIN`).

## Testing

- **Django `TestCase`** via `python manage.py test --parallel`. No pytest, no `APITestCase`, no
  factory_boy, no fixture files, no `conftest.py`.
- **Extend `core/tests.py::BaseTestCase`.** Its `setUp` builds knox auth headers
  (`self.admin_token`, `self.manager_token`, `self.seller_token`, `self.issuer_token` via
  `utils/test_utils.get_auth_header(role)`) plus a full object graph (`self.customer`,
  `self.supplier`, `self.airline`, `self.departure_airport`, `self.arrival_airport`, `self.flight`,
  `self.sale`, `self.reservation`).
- Call the real URL with the Django test client:
  `self.client.post("/agency/customers/", data=..., headers=self.admin_token, content_type="application/json")`.
- Assert on `response.data["success"]`, `response.data["reason"] == <Enum>.MEMBER.value`, and DB
  counts. Missing auth → `assert response.status_code == 401`; forbidden role → `403`.
- Cover each `validate_data` branch and each `FailureReason`, plus `transaction.atomic` rollback and
  role-scoped output. Layout: package `agency/tests/test_<resource>.py`, or single `<app>/tests.py`.

## Config & env

`core/settings.py` calls `load_dotenv()` and reads (all optional, comma-split where a list):
`DJANGO_SECRET_KEY` (falls back to a **random per-process** value — set it in real deploys),
`ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `CORS_ALLOWED_ORIGINS`, `DATABASE_URL` (else the hardcoded
local `agency` DB), `RAILWAY_ENVIRONMENT` (presence ⇒ production). No `.env.example`.

## Known inconsistencies — do not propagate

- **Business errors at HTTP 200** — keep matching it for consistency with existing endpoints, but
  it's debt; a future migration to real status codes is desirable.
- **No `DEFAULT_PERMISSION_CLASSES`** — every new view must remember `permission_classes` or it ships
  public.
- `users/views.py::LastSeenView` is implemented but **not routed**; `User.last_access` is never
  updated in the real flow.
- `validate_data()` is near-duplicated across every Mixin — a shared helper is a reasonable refactor.
- `Flight.clean()` is bypassed by direct `.objects.create()`.
- `core/` holds app-like modules (`models.py`, `admin.py`, `tests.py`, `utils.py`) alongside project
  config; `utils/` (root) and `core/utils.py` overlap.
- `black` is a dependency but unconfigured/unused; no isort/mypy/pre-commit.
